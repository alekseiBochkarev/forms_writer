# ТЗ: вводные/заключительные части, поток «новых тестов» и переименование фото-тестов

Основание: `docs/dzen_research.md` §7–10 и дополнительные вводные заказчика
(Telegram-канал `qa_helper_draft`, три задачи).

Статус: черновик к реализации. Открытые вопросы — в разделе 9.

## 1. Цель

1. Повысить читаемость выпусков за счёт вводной/заключительной части и
   обязательного ревью (задача 1).
2. Запустить отдельный поток «новых тестов» с публикацией в Telegram-канал
   `qa_helper_draft` (задача 2).
3. Переработать именование фото-тестов по формуле из §10 (задача 3).

## 2. Границы (объём)

Входит:
- Генерация intro (2–4 абзаца) и outro (1–3 абзаца) для эрудиционного потока.
- Отдельный шаг ревью с результатом OK/правки перед публикацией.
- Новый режим/поток «новых тестов» с собственным состоянием и расписанием.
- Настройка публикации в канал `@qa_helper_draft`.
- Библиотека шаблонов заголовков фото-тестов и защита от повторов.

Не входит:
- Изменение логики подбора изображений/vision.
- Редактирование уже опубликованных форм.
- Смена модели/провайдера LLM.
- Правовая проверка лицензий изображений.

## 3. Функциональные требования

### Задача 1. Вводная и заключительная + ревью (эрудиция)

1.1. После генерации вопросов генерировать intro (2–4 абзаца) и outro (1–3
     абзаца) по шаблону §8. Вводная не должна содержать правильных вариантов,
     их синонимов и узнаваемых подсказок.
1.2. Промпт вводной получает только список broad-тем вопросов
     (`q["topic"]`) либо 3–5 отраслей; ответы/опции в промпт вводной не
     передаются.
1.3. Ревью — отдельный шаг пайплайна (`review.py`), отдельный LLM-вызов(ы),
     результат `OK` или список правок. Проверяет: спойлеры, соответствие анонса
     фактическим темам, отсутствие шаблонности/повторов с прошлыми выпусками,
     наличие инструкции по ответам и CTA в outro.
1.4. Политика при `правки`: по умолчанию — один автоматический регенеративный
     проход; если снова не OK — публикация блокируется (код возврата != 0).
     Настраиваемо.
1.5. Хранение: intro/outro — поля выпуска в `state.json`
     (`published[].intro/outro`), чтобы ревью могло сверяться с прошлыми.
1.6. Размещение в форме: intro — блок `comment` в начале формы, outro — блок
     `comment` в конце. Добавить метод
     `YandexFormsClient.add_comment_question(survey_id, label, header=False)`.
     Проверить, что `comment`-блоки не влияют на `quiz` scoring (см. риски).
1.7. Конфиг: `INTRO_ENABLED`, `CONCLUSION_ENABLED`, `REVIEW_ENABLED`,
     `REVIEW_MAX_ATTEMPTS`, `INTRO_MIN/MAX_PARAGRAPHS`,
     `OUTRO_MIN/MAX_PARAGRAPHS`, опционально `REVIEW_MODEL`.

### Задача 2. Новый поток тестов (канал qa_helper_draft)

2.1. Новый режим `mode="new_tests"` (отдельно от `erudition` и `photo`).
2.2. Собственные: CLI-флаг `--new-tests`, `NEW_TESTS_STATE_FILE`
     (напр. `new_state.json`), workflow `daily_new_tests.yml`, cron.
2.3. Число вопросов и порог — параметры:
     `NEW_TESTS_COUNT`, `NEW_TESTS_PASS_SCORES`, `NEW_TESTS_MIN_QUESTIONS`.
     Рекомендация §9: 10 вопросов с порогом `7/10` или `8/10`
     (формат «Позитивного Холста»), либо 15 с `10/15`. Выбор — за заказчиком
     (см. открытые вопросы).
2.4. Темы: узнаваемые/ностальгические (советское кино, советские актёры,
     сказки, кулинария, география, жители городов) + общий кругозор.
     `NEW_TESTS_TOPICS` (JSON-массив), ротация с исключением использованных
     (аналогично `photo_flow._choose_theme`, `photo_flow.py:353`).
2.5. Вводная обязательна для каждого выпуска; заключительная — по формату.
     Переиспользовать логику задачи 1 и тот же модуль ревью.
2.6. Публикация: Telegram-канал `@qa_helper_draft`; предусмотреть
     `NEW_TESTS_TG_TARGET_CHANNEL` для переопределения (если каналы
     разойдутся). VK — опционально.
2.7. Антидубли: вопросы не повторяют ни эрудицию, ни фото-поток (общий
     `DuplicateChecker`, `dedup.py`), либо отдельная история.

### Задача 3. Именование фото-тестов

3.1. Заменить формулу `photo_flow.py:485`
     (`f"{PHOTO_SURVEY_NAME}? {Тема}"`) на
     `build_survey_name(cfg, theme, count)` по формуле §10.3:
     `[ставка/идентичность] + [конкретная категория] + [число/порог]`.
3.2. Число вопросов — `len(questions)` (доступно после `_build_questions`,
     `photo_flow.py:473`).
3.3. Библиотека 5–8 шаблонов на тему (§10.4); выбор случайный с запретом
     повторов последних N выпусков (по аналогии с проверкой
     `used_entities`). Хранить `used_titles` в `photo_state.json`.
3.4. Сузить темы до узнаваемых подгрупп, обновив `DEFAULT_PHOTO_THEMES`
     (`config.py:61`) и/или `PHOTO_THEMES`: вместо «животные» — «породы собак»,
     «хищные птицы»; вместо «картины» — «картины из школьной программы»,
     «пейзажи русских художников»; «советское кино» в приоритете (требует
     `FILM_RU_ENABLED=true`).
3.5. Фолбэк: если шаблон неприменим — `PHOTO_SURVEY_NAME`
     (`config.py:141`), а не пустое имя.
3.6. Проверка заголовка на спойлер: в имени не должно быть слов из правильных
     ответов выпуска (то же ревью).
3.7. Нумерация `next_survey_name` сохраняется в названии формы Яндекс Форм, но в
     анонс Telegram/VK идёт базовый заголовок без счётчика (решение заказчика).

## 7. Критерии приёмки

1. Эрудиционный выпуск содержит в форме intro (2–4 абзаца) перед вопросами и
   outro (1–3 абзаца) после; в intro нет правильных ответов (проверяется
   ревью). `pytest tests/` зелёный.
2. Ревью — отдельный шаг: при не-OK и исчерпании попыток форма не публикуется,
   код возврата != 0.
3. `main.py --new-tests --dry-run` строит план N вопросов по выбранной теме и
   не обращается к API; боевой запуск публикует форму и постит в
   `@qa_helper_draft`.
4. Состояние потоков разделено (`state.json`, `new_state.json`,
   `photo_state.json`); повтор в тот же день блокируется.
5. Имя фото-теста соответствует формуле §10.3, содержит число `len(questions)`
   и не повторялось последние N выпусков; темы сужены; при неудаче —
   `PHOTO_SURVEY_NAME`.
6. Заголовок фото-теста не содержит слов из правильных ответов.

## 9. Риски и открытые вопросы

Риски:
- Тип `comment` может учитываться в `question_count`/scoring квиза — требуется
  ручная проверка на реальной форме (см. §6 API).
- Вводная в форме vs в анонсе: смысл разных мест отличается; нужен выбор.
- Дополнительные LLM-вызовы (intro/outro/review/регенерации) увеличивают
  бюджет времени workflow — пересчитать `timeout-minutes` (`daily.yml:21`).
- Сужение тем фото-тестов упирается в доступность источников:
  «советское кино» требует `FILM_RU_ENABLED`.
- numeric id канала: использовать `@qa_helper_draft`.

Решения заказчика (2026-10-06):
1. Вводная/заключительная пишутся И в форму (блоки `comment`), И в анонс Telegram.
2. Ревью — LLM; при не-OK публикация блокируется.
3. Новый поток — 15 вопросов, порог 10/15.
4. Темы нового потока — общая эрудиция + наиболее популярные направления
   (кино, актёры, сказки, кулинария, география и т.д.).
5. Бот `qa_helper_editor` (один на всё) назначен админом каналов; токен в
   `TG_BOT_TOKEN`. Старые тесты (эрудиция/фото) публикуются в отдельный канал
   (`TG_TARGET_CHANNEL`, задаётся явно), новые — в `@qa_helper_draft`
   (`NEW_TESTS_TG_TARGET_CHANNEL`).
6. VK не используется (`PUBLISH_VK=false`, `NEW_TESTS_PUBLISH_VK=false`).
7. Нумерация сохраняется в названии формы Яндекс Форм, но в анонс TG/VK идёт
   базовый заголовок без счётчика.
8. `FILM_RU_ENABLED=true` — эксперимент, сначала для нового проекта.
9–10. Пояснения даны в чате (окно анти-повторов заголовков; состав для живой
   проверки).
