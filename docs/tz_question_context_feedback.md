# ТЗ: «завязка» и пояснения к вопросам + режим мгновенной обратной связи

Статус: к реализации (итерация 1).
Основание: разбор каналов «Тесты от Эйнштейна» и «#голоса» (`docs/dzen_research.md`,
разделы 7–10) и проверка API Яндекс Форм (см. §4).

## 1. Цель

Поднять дочитывание и вовлечённость (комментарии, повторные заходы) за счёт двух
приёмов, которые в разобранных каналах дают основной эффект:

1. **Завязка (`context`)** — 1–2 предложения живой сценки/детали перед вопросом.
   Вопрос перестаёт быть экзаменационным, становится историей.
2. **Пояснение (`explanation`)** — 2–3 предложения «почему это верно» с фактом.
   Показывается **сразу после верного выбора** (режим обратной связи), а не
   списком в конце, чтобы не спойлерить тест.

Приём «нарезать тест на N форм по одному вопросу» и заголовки-ставки в этой
итерации **не делаем** (см. §9).

## 2. Объём итерации

| # | Что | Флаг | По умолчанию |
|---|---|---|---|
| 1 | Завязка перед вопросом | `QUESTION_CONTEXT_ENABLED` | `true` |
| 2 | Пояснение + мгновенная обратная связь | `FEEDBACK_ENABLED` | `false` |

Завязка включается сразу: она безопасна (не меняет подсчёт баллов) и не требует
новых сущностей API кроме текста вопроса.

Обратная связь — переключатель формата, поэтому по умолчанию выключена: в этом
режиме квиз перестаёт считать баллы (см. §5.3), и включать его нужно осознанно,
сначала на одном выпуске (`--force`).

## 3. Контентные требования к полям

### 3.1 `context` (завязка)

- 1–2 предложения, 120–240 символов, до 300 с запасом (`QUESTION_CONTEXT_MAX_CHARS`).
- Конкретная сценка, деталь, бытовая или историческая рамка: «Откроешь в театре
  программку, а там на полстраницы рассказ о том, что сейчас случится».
- **Не содержит правильного ответа** ни целиком, ни всеми значимыми словами.
- Не пересказывает формулировку вопроса и не содержит ответов на другие вопросы.
- Не начинается с «А вы знали…», без риторических вопросов и без воды.
- Пишется в настоящем времени, нейтрально-дружелюбно, без «я».

### 3.2 `explanation` (пояснение)

- 2–3 предложения, 200–420 символов (`EXPLANATION_MAX_CHARS`).
- Объясняет, **почему** верный вариант верен, и добавляет один проверяемый факт.
- Не повторяет дословно текст вопроса и не перечисляет остальные варианты.
- Не содержит ссылок, рекламы и призывов.

Оба поля генерирует та же модель, что и вопросы (один вызов, расширенная схема
JSON). Ошибка/пустое поле не роняет выпуск: поле просто не выводится
(для `context`) или вопрос идёт без пояснения (для `explanation`).

## 4. Проверка API (выполнена на реальном стенде)

Проверено на `api.forms.yandex.net/v1` одноразовой формой (создана и удалена):

- `POST /surveys/{survey_id}/questions/` с `?with_slugs=true` возвращает
  `slug` вопроса (`id-enum-<id>`) и `slug` каждого варианта.
- `POST /surveys/{survey_id}/questions/{question_id}/conditions` принимает:

  ```json
  {
    "operator": "and",
    "items": [
      {"type": "question", "condition": "eq",
       "question": "id-enum-145832886", "value": "394634091"}
    ]
  }
  ```

  и возвращает `{id, operator, items}`; для «любого из неверных» —
  `operator: "or"` и по одному `eq` на каждый неверный вариант.
- `GET .../conditions` возвращает сохранённое условие.
- Публикация формы с условиями работает (`POST /surveys/{id}/publish/`).
- Вопросы поддерживают поле `comment` («подсказка», до 1000 символов) и
  `label` до 8000 символов — завязку кладём в `label` (как в эталоне:
  `«<завязка>\n\n<вопрос>»`), чтобы она читалась одним блоком.
- **Грабли:** `PATCH /questions/{id}` заменяет вопрос целиком; без `type` в теле
  вопрос превращается в `string`. Мы вопросы не патчим — только создаём.

## 5. Механика

### 5.1 Завязка (всегда, при `QUESTION_CONTEXT_ENABLED=true`)

`label` вопроса = `context.strip() + "\n\n" + question` (если `context` непустой).
Пустой `context` — `label` = `question` (обратная совместимость).

### 5.2 Санитайзер спойлеров

Перед созданием формы (в `publish_questions`, то есть для всех потоков) завязки
проверяются детерминированно: если в `context` встречается правильный ответ
целиком или все его значимые слова — `context` очищается, в лог уходит warning.
Выпуск не блокируется.

### 5.3 Режим обратной связи (`FEEDBACK_ENABLED=true`)

На каждый вопрос, сразу после него, добавляются два блока `comment`:

| Блок | Условие показа | Текст |
|---|---|---|
| «верно» | ответ `eq` правильному варианту | `FEEDBACK_CORRECT_TEXT` + пояснение |
| «неверно» | ответ `eq` любому неверному (`or`) | `FEEDBACK_WRONG_TEXT` |

Настройки квиза (`quiz`: сегменты, показ результатов) в этом режиме **не
применяются**: читатель может менять вариант до попадания, поэтому баллы и
сегменты теряют смысл. Результат — самооценка «сколько раз попал с первой
попытки», о ней просит заключительная часть (см. §8).

Если создать условие не удалось — публикация падает с `YandexFormsError`
(fail-closed): форма с всегда видимым блоком «Ошибочка» хуже, чем непublished
форма. Анонс при этом не отправляется.

Порядок блоков: вводная → (вопрос → 2 блока обратной связи) × N →
заключительная. Вводная и заключительная остаются `comment`-блоками без условий.

## 8. Связка с вводной/заключительной

- Во вводной завязки **не** используются (там свои правила из §8
  `docs/dzen_research.md`), ревью не меняется.
- При `FEEDBACK_ENABLED=true` заключительная должна просить самооценку
  («сколько раз выбрали верный ответ с первой попытки»). Это правка промпта
  `_build_outro_prompt` по флагу: вместо «посмотреть правильные ответы» —
  «сколько раз попали с первой попытки».
- Ревью (`review.py`) остаётся обязательным как есть; новые поля в него не
  передаются, чтобы не удорожать выпуск.

## 9. Что НЕ входит в итерацию

1. **Нарезка на N форм по одному вопросу** — сильно меняет пайплайн и статистику;
   нужно отдельное решение по площадке (Дзен vs Telegram).
2. **Заголовки-ставки для основного потока** («Вы человек с широким кругозором,
   если ответите на 9/12»). Блокер: `SURVEY_NAME` участвует в нумерации
   (`next_survey_name`) и в `--delete-survey`/загрузке истории по префиксу имени.
   Сначала нужно развязать имя формы и номер выпуска (хранить `survey_id` в
   состоянии), иначе сломается удаление и защита от дублей. Для фото-тестов и
   рубрик формула уже есть.
3. **Бонусный вопрос вне зачёта + закреплённый комментарий** — нет API постов в
   Дзен, остаётся ручным шагом.
4. **Фото-поток** — там фиксированная формулировка и картинка; завязка/пояснение
   добавляются отдельной итерацией.
5. **Рубрики** — завязки и обратная связь в формах рубрик не выводятся (метрики
   рубрик считаются по баллам квиза), поэтому для них поля у модели не
   запрашиваются (`rubric_flow._llm_cfg`).

## 10. Тесты

- `test_llm.py`: в промпте появляются поля `context`/`explanation` только при
  включённых флагах; `_validate_questions` обрезает по лимиту, чистит пробелы,
  не падает на пустых/битых значениях; `correct_index` не сдвигается.
- `test_review.py`: спойлер в завязке очищается; без спойлера — сохраняется;
  частичное совпадение слов ответа не считается спойлером.
- `test_yandex_forms.py`: `label` собирается из завязки и вопроса; условия
  отправляются с правильными `question`/`value`; блоки идут после вопроса;
  `quiz` не применяется в режиме обратной связи; при ошибке условий публикация
  падает.
- `test_config.py`: дефолты и парсинг новых переменных.
- `test_main.py`: `load_questions_from_file` сохраняет `context`/`explanation`.

## 11. Риски

| Риск | Мера |
|---|---|
| Модель кладёт ответ в завязку | детерминированный санитайзер + правило в промпте |
| Завязка раздувает вопрос | лимит символов + обрезка по границе предложения |
| Условия показа не сработают на боевой форме | проверено на стенде; при ошибке — fail-closed |
| Обратная связь ломает сегменты | режим явно выключен по умолчанию |
| Удорожание выпуска | `explanation` запрашивается только при включённом режиме |
