# forms_writer

Автоматическое создание и публикация тестов-викторин в **Яндекс Формах**.

Приложение раз в день генерирует вопросы на общую эрудицию с помощью LLM
(OpenAI-совместимый API), собирает из них тест с правильными ответами,
перемешиванием вариантов и сегментами результатов — и публикует форму.

## Возможности

- Генерация вопросов через любую OpenAI-совместимую модель (`/chat/completions`).
- Создание новой формы **или** добавление вопросов в существующую.
- 4 варианта ответа на вопрос, один правильный, автоматическая пометка верного.
- Все вопросы обязательные (нельзя отправить форму с пропусками).
- Защита от повторов: вопросы прошлых выпусков запоминаются и не повторяются.
- Перемешивание вариантов (`shuffle`).
- Публичный доступ к форме: ссылка открывается у обычных пользователей без авторизации.
- Счётчик в названии формы (`… 2`, `… 3`, …), чтобы не путать выпуски.
- Настройка теста: показ результатов, показ правильных ответов, статистика ответов.
- Сегменты результатов (диапазоны баллов) или порог прохождения.
- Публикация анонса формы в **Telegram** и **VK**.
- Защита от повторной публикации в один день (файл состояния `state.json`).
- Ежедневный запуск через GitHub Actions, а также ручной запуск и `--dry-run`.
- **Вводная и заключительная части** теста (блоки `comment` в форме) и
  **обязательное LLM-ревью** на спойлеры/шаблонность перед публикацией
  (модуль `review.py`).
- **Фото-тесты** (`python main.py --photo`): выпуск на одну тему с изображениями,
  автоподбор фото из открытых источников и опциональная проверка vision-моделью.
  Заголовок собирается по формуле «ставка + конкретная категория + число фото».
- **Поток «новых тестов»** (`python main.py --new-tests`): отдельные состояние,
  темы и Telegram-канал (`@qa_helper_draft`), 15 вопросов с порогом 10/15.

## Структура

```
forms_writer/
├── main.py                  # точка входа и CLI
├── config.py                # загрузка настроек из окружения
├── llm.py                   # генерация вопросов, вводной и заключительной
├── review.py                # отдельный LLM-проход ревью перед публикацией
├── yandex_forms.py          # клиент API Яндекс Форм

├── state.py                 # состояние: защита от дублей и список заданных вопросов
├── photo_flow.py            # фото-поток: один выпуск на одну тему
├── photo_sources.py         # поиск изображений (Wikimedia, Openverse и др.)
├── vision.py                # проверка изображений vision-моделью
├── requirements.txt
├── .env.example             # шаблон настроек для локального запуска
├── state.json               # данные о последних публикациях (эрудиция)

```

## Быстрый старт (локально)

```bash
git clone <ваш-репозиторий>
cd forms_writer
python -m venv .venv
# Windows: .venv\Scripts\activate
# Linux/macOS: source .venv/bin/activate
pip install -r requirements.txt

cp .env.example .env   # заполните .env
python main.py --dry-run
python main.py
```

Проверить доступ к API Яндекс Форм и посмотреть свои формы:

```bash
python main.py --check
```

Служебные команды (по id формы):

```bash
python main.py --rename-survey 6aac... --name "Насколько широк ваш кругозор 1"
python main.py --delete-survey 6aac...
```

Бюджет времени LLM в эрудиционном потоке:
`LLM_TIMEOUT × (LLM_RETRIES + 1 + 1) × max_attempts` должен укладываться в
`timeout-minutes` workflow (дополнительный `+1` — возможный fallback-запрос на
внешнюю попытку). При дефолтах `120 × (1+1+1) × 3 = 1080 с = 18 мин < 25 мин`
(`.github/workflows/daily.yml`). Не увеличивайте эти настройки, не подняв
`timeout-minutes`.

Фото-поток делает много LLM-вызовов на выпуск (~15 при 10 вопросах: сущности и
дистракторы), поэтому его бюджет считается отдельно, а `timeout-minutes` в
`.github/workflows/daily_photo.yml` заметно больше.

## Публикация анонса в Telegram и VK

После создания формы приложение публикует короткий анонс со ссылкой.

Публикация включается автоматически, если заданы соответствующие переменные:

- **Telegram:** `TG_BOT_TOKEN` + `TG_TARGET_CHANNEL` (токен бота, добавленного
  администратором в канал).
- **VK:** `VK_ACCESS_TOKEN` + `VK_GROUP_ID` (токен с правом `wall`; id группы —
  положительное число, пост публикуется от имени группы).

Текст анонса настраивается через `ANNOUNCE_TEMPLATE` (одна формулировка) или
`ANNOUNCE_TEMPLATES` (JSON-массив). Доступны подстановки `{name}`, `{count}`,
`{url}`, `{date}`.

Если ничего не задано, используется **встроенный набор формулировок** — при каждом
запуске выбирается случайная, поэтому посты в TG и VK слегка отличаются:

```text
Новый тест: «{name}»

{count} вопросов на разные темы — проверьте свой кругозор.

Пройти: {url}
```

Пример своего списка:

```bash
ANNOUNCE_TEMPLATES=["Вариант А: «{name}» — {url}","Вариант Б ({count} вопросов): {url}"]
```

Если ключи не заданы — публикация в соцсети просто пропускается.

Перед публикацией приложение выставляет форме **публичный доступ** на заполнение
(`POST /surveys/{id}/access` с `action: submit`, `access: public`), поэтому ссылка
вида `https://forms.yandex.ru/u/{id}/` открывается без авторизации у любого
пользователя.

### Сегменты результатов

Если `SEGMENTS` не задан, приложение строит 4 сегмента по четвертям от общего
числа баллов, с разными названиями и описаниями, привязанными к числу верных
ответов, например для 13 вопросов:

- `0–3` — «Начинающий»
- `4–6` — «Любознательный»
- `7–9` — «Эрудит»
- `10–13` — «Ходячая энциклопедия»

В админке Яндекс Форм нижняя граница сегмента отображается как «предыдущая + 0,01»
(это внутренний формат сервиса); фактические границы указаны в описании.

## Вводная, заключительная и ревью

Перед публикацией для теста генерируются **вводная** (2–4 абзаца) и
**заключительная** (1–3 абзаца) части (шаблон из `docs/dzen_research.md` §8).
Вводная вставляется в форму **первым** блоком, заключительная — **последним**
(тип блока `comment`, он не влияет на баллы квиза). Дополнительно вводная
добавляется в текст Telegram-анонса перед ссылкой (управляется `ANNOUNCE_INTRO`).

В промпт вводной передаются только широкие темы вопросов (`q["topic"]`) — без
ответов и вариантов, чтобы не подсказать правильный ответ.

После генерации запускается **отдельный LLM-проход ревью** (`review.py`):
проверка спойлеров (есть и детерминированная проверка слов из правильных
ответов), соответствия анонса фактическим темам, отсутствия шаблонности и
наличия инструкции/CTA в заключительной. Результат — `ok` или список замечаний.

- Если ревью не прошло, вводная/заключительная генерируются заново —
  до `REVIEW_MAX_ATTEMPTS` раз.
- Если ревью не прошло после всех попыток, **форма не публикуется**, код
  возврата != 0.
- При сбое самого LLM-ревью результат fail-closed (не публикуем).

Отключить можно флагами `INTRO_ENABLED`, `CONCLUSION_ENABLED`, `REVIEW_ENABLED`.
Если вопросы берутся из `QUESTIONS_FILE`, а `LLM_API_KEY` не задан (запуск без
LLM), вводная/заключительная и ревью пропускаются — форма собирается из готовых
вопросов, как раньше.

## Поток «новых тестов»

Отдельный поток запускается флагом `--new-tests` и публикуется в собственный
Telegram-канал (`NEW_TESTS_TG_TARGET_CHANNEL`, по умолчанию `@qa_helper_draft`).
VK для этого потока по умолчанию выключен (`NEW_TESTS_PUBLISH_VK=false`).

- Гейт: `NEW_TESTS_ENABLED=true`.
- 15 вопросов (`NEW_TESTS_COUNT`) с порогом 10/15 (`NEW_TESTS_PASS_SCORES`).
- Темы: общая эрудиция и наиболее популярные направления из исследования
  (`NEW_TESTS_TOPICS`: кино, актёры, сказки, кулинария, география и др.),
  ротация с исключением использованных.
- Собственное состояние — `new_state.json`; повтор в тот же день блокируется.
- Вводная обязательна, заключительная — по формату; ревью то же, что и в
  эрудиции.

```bash
python main.py --new-tests --dry-run   # план без обращения к API
python main.py --new-tests             # боевой выпуск
```

`--new-tests --dry-run` работает даже при `NEW_TESTS_ENABLED=false` и не
публикует форму. Чтобы построить план, нужен источник вопросов: либо
`LLM_API_KEY` (генерация), либо `QUESTIONS_FILE` с готовыми вопросами. Внешние
API Яндекса и соцсетей в этом режиме не вызываются.

> **Важно про канал.** Bot API принимает `@username` (например
> `@qa_helper_draft`) либо id вида `-100...`. Числовой web-id канала
> (`-3728753106`) для Bot API **не подходит**. Бот должен быть администратором
> канала.

## Защита от дублей и повторов вопросов

Приложение хранит в `state.json` дату последней публикации и список уже заданных
вопросов (`asked_questions`).

- Если запуск повторяется в тот же день (например, резервным расписанием),
  форма не создаётся заново. Для принудительного запуска — `--force` или `FORCE=true`.
- Перед генерацией список прошлых вопросов передаётся модели с требованием не
  повторяться, а после генерации вопросы дополнительно проверяются на совпадения
  (точные и похожие формулировки). Повторы отбрасываются и генерируются заново.

Список хранит последние 500 вопросов, поэтому защита работает и спустя много выпусков.

## Фото-тесты

Отдельный поток выпускает тест, в котором каждый вопрос сопровождается фотографией.
Каждый выпуск посвящён **одной теме** (например «советские фильмы», «советские
актёры» или «советские актрисы»), формулировка у всех вопросов общая:

- темы про фильмы → «Кадр из какого фильма?»;
- темы про актёров/актрис → «Кто на фото?»;
- остальные темы → «Что (кто) изображено на фотографии?».

У каждого вопроса 4 варианта: один верный и три дистрактора **строго того же класса**
(их генерирует LLM). Подсказки (год, режиссёр и т.п.) не добавляются.

### Запуск

```bash
# фото-поток включается переменной PHOTO_FLOW_ENABLED=true
python main.py --photo                              # тема выбирается случайно
python main.py --photo --photo-theme "советские фильмы"
python main.py --photo --photo-theme "советские актрисы"
python main.py --photo --dry-run                    # показать план без публикации
python main.py --photo --force                       # игнорировать защиту от дублей
```

В `--dry-run` приложение генерирует сущности и варианты через LLM, показывает
найденные URL кандидатов, но **не скачивает изображения, не обращается к Яндекс
Формам и не проверяет фото через vision** (это явно пишется в лог). Состояние не
обновляется.

### Откуда берутся фото

Источник подбирается по теме выпуска:

- **советские фильмы/актёры/актрисы (любая тема с «совет»/«СССР»)** →
  `ruwiki_film` (ru.wikipedia, файловый namespace), работает только при
  `FILM_RU_ENABLED=true`;
- **иностранные фильмы/кино/сериалы** → `filmgrab` и `movscreencaps` (по флагам
  `FILM_GRAB_ENABLED`/`MOVIE_SCREENCAPS_ENABLED`);
- **остальные темы** (породы собак, хищные птицы, животные Африки, картины
  из школьной программы, пейзажи, достопримечательности и т.п.) → `wikimedia` +
  `openverse`.

Для кино-тем открытые `wikimedia`/`openverse` **не примешиваются**: там нет
кадров фильмов, и до этого вместо кадров в тест попадали постеры и афиши.

`PHOTO_SOURCES` задаёт только открытые `wikimedia`/`openverse`. Кино-источники
(`ruwiki_film`, `filmgrab`, `movscreencaps`) включаются **исключительно** своими
флагами `FILM_RU_ENABLED` / `FILM_GRAB_ENABLED` / `MOVIE_SCREENCAPS_ENABLED`;
их имена в `PHOTO_SOURCES` ничего не включают. Тема считается доступной, только
если хотя бы один её источник реально включён, — иначе она пропускается.

Кино-источники по умолчанию **выключены**, так как их права/лицензии
рискованнее. Если тема фильмов выбрана, а нужный флаг не включён, тема
**пропускается** (с записью в логе), и выбирается другая; если доступных тем не
осталось — запуск завершается понятной ошибкой.

Для Wikimedia обязателен описательный `WIKIMEDIA_USER_AGENT`: если источник активен,
а переменная не задана, приложение выводит предупреждение (но не падает).

Автор и лицензия каждого использованного изображения сохраняются **только** в
`photo_state.json` (поле `images` в записи выпуска) и не попадают ни в форму, ни в
анонс.

### Проверка изображений (vision)

Проверку того, что на фото действительно нужная сущность, выполняет vision-модель
(OpenAI-совместимый API с поддержкой изображений). По умолчанию она **включена**
(`PHOTO_VISION_ENABLED=true`), поэтому нужна vision-совместимая модель
(`VISION_MODEL` или `LLM_MODEL`). Проверка выполняется по каждому кандидату и
учитывает класс изображения:

- **фильмы** — принимается только настоящий кадр/сцена; постеры, афиши, обложки,
  фото музейных экспонатов/памятников, страницы книг и скриншоты отклоняются;
- **актёры/актрисы** — принимается только узнаваемый портрет человека; статуи,
  рисунки, групповые и неясные снимки, афиши и текст отклоняются;
- **остальные темы** — отклоняются изображения, состоящие в основном из текста
  (документы, таблички, скриншоты, водяные знаки, логотипы), коллажи и мемы.

Проверка работает по принципу **fail-closed**: если vision-API недоступен, ответ
не распознан или модель сообщила о замечаниях, кандидат отклоняется. Это надёжнее
от мусора, но при сбое API выпуск может недобрать вопросы — тогда он не
публикуется (см. `PHOTO_MIN_QUESTIONS`).

Чтобы полностью отключить проверку (изображения используются без обращения к
сети), задайте `PHOTO_VISION_ENABLED=false`.

Число вопросов задаётся `PHOTO_QUESTIONS_COUNT` (по умолчанию 10). Если удалось
подготовить меньше `PHOTO_MIN_QUESTIONS` (по умолчанию равно числу вопросов),
выпуск не публикуется.

### Название фото-теста

Имя формы собирается по формуле §10.3 исследования — «ставка/идентичность +
конкретная категория + число вопросов», например:

- «Узнайте советский фильм по одному кадру. 10 вопросов»
- «Породы собак: узнаете ли вы каждую из 10 по фото?»
- «Вы помните эти 10 картин из школьной программы? Проверьте по фото»

Шаблоны по категориям заданы встроенно и переопределяются JSON-объектом
`PHOTO_TITLE_TEMPLATES` (ключ — категория, `{count}` — число вопросов). Заголовки
со словами из правильных ответов отбрасываются (спойлер), а уже использованные в
последних `PHOTO_TITLE_HISTORY` выпусках — по возможности не повторяются.
Если применимого шаблона нет — фолбэк на `PHOTO_SURVEY_NAME` с темой, например
«Что на фото? Животные Африки». Темы по умолчанию сужены до узнаваемых подгрупп
(советское кино и актёры в приоритете).

Состояние фото-потока хранится отдельно — в `photo_state.json`: дата последней
публикации, список выпусков (`title` в записи), использованные заголовки, темы и
сущности (чтобы не повторяться). Анонс публикуется теми же шаблонами, что и для
эрудиции (`ANNOUNCE_TEMPLATES`).

## Как получить токен и org id

1. **Токен Яндекс Форм.** Создайте OAuth-приложение на <https://oauth.yandex.ru>
   («Для доступа к API или отладки»), добавьте доступ
   **«Изменение настроек форм (forms:write)»**, затем откройте
   `https://oauth.yandex.ru/authorize?response_type=token&client_id=<ClientID>`
   и скопируйте токен.
2. **Org id.** В Яндекс Трекере: `https://tracker.yandex.ru/admin/orgs` →
   значение поля «Идентификатор». Для Yandex Identity Hub используйте
   `YANDEX_ORG_ID` как Cloud Org ID и заголовок `X-Cloud-Org-Id`.
3. API Яндекс Форм доступно для **«Форм для бизнеса» (Яндекс 360)**.

## Ежедневный запуск в GitHub Actions

1. Запушьте проект в репозиторий.
2. **Settings → Secrets and variables → Actions**:
   - **Secrets:** `LLM_API_KEY`, `YANDEX_FORMS_TOKEN`, `YANDEX_ORG_ID`
     и, для соцсетей, `TG_BOT_TOKEN`, `TG_TARGET_CHANNEL`,
     `VK_ACCESS_TOKEN`, `VK_GROUP_ID`;
   - **Variables** (необязательно): `LLM_BASE_URL`, `LLM_MODEL`,
     `QUESTIONS_TOPIC`, `QUESTIONS_COUNT`, `QUESTIONS_LANGUAGE`.
3. Расписание задаётся в `.github/workflows/daily.yml` (cron в UTC: основной
   `0 6 * * *` и резервный `30 6 * * *`). Запустить можно и вручную:
   вкладка **Actions → Daily form → Run workflow**.
4. Workflow сам коммитит обновлённый `state.json` (нужны права
   `permissions: contents: write`, они уже указаны).

Фото-тесты запускаются отдельным workflow `.github/workflows/daily_photo.yml`
(шаблон `Daily photo form`) по cron `0 16 * * *` и `30 16 * * *` (UTC), то есть
примерно на 10 часов позже эрудиционного выпуска. Он выполняет
`python main.py --photo` и коммитит только `photo_state.json` (перед push делает
`git pull --rebase`). Запустить вручную: **Actions → Daily photo form → Run workflow**.

Поток «новых тестов» запускается отдельным workflow
`.github/workflows/daily_new_tests.yml` (шаблон `Daily new tests form`) по cron
`0 12 * * *` и `30 12 * * *` (UTC). Он выполняет `python main.py --new-tests`
с `NEW_TESTS_ENABLED=true` и коммитит `new_state.json`. Запустить вручную:
**Actions → Daily new tests form → Run workflow**.

Каналы публикации: эрудиция, фото и новые тесты постят в Telegram. Для старого
потока канал задаётся секретом `TG_TARGET_CHANNEL` (для `@qa_helper_draft`), для
нового — `NEW_TESTS_TG_TARGET_CHANNEL`. Помните, что Bot API принимает
`@username` или `-100...`, а не web-id канала.

## Формат вопросов в `QUESTIONS_FILE`

```json
{
  "questions": [
    {
      "topic": "История",
      "question": "В каком году пала Западная Римская империя?",
      "options": ["395", "410", "476", "1453"],
      "correct_index": 2
    }
  ]
}
```

## Безопасность

- Не коммитьте `.env` и не храните токены в коде — используйте секреты GitHub.
- Выдавайте токену минимально необходимый доступ (`forms:write`) и отзывайте его,
  когда он больше не нужен.
- Токен даёт полный доступ ко всем вашим формам — обращайтесь с ним аккуратно.

## Ограничения

- API Яндекс Форм работает только для форм в составе организации (Яндекс 360).
- Генерация вопросов требует доступа к LLM API; при недоступности используйте
  `QUESTIONS_FILE` с заготовкой.
